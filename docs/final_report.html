Relatório Técnico

FIAP Pós-IA Fase 2: Tech Challenge - Sistema de Análise Nutricional SISVAN

Algoritmo Genético Co-Evolutivo e Agente LLM ReAct

1. Resumo Executivo

Este relatório apresenta o desenvolvimento e implementação de um sistema completo de análise e previsão de estado nutricional baseado em dados do SISVAN (Sistema de Vigilância Alimentar e Nutricional). O projeto integra técnicas avançadas de Machine Learning com Inteligência Artificial Generativa, utilizando um algoritmo genético co-evolutivo para otimização de hiperparâmetros e um agente LLM ReAct para análise clínica interativa.

Principais Conquistas:
  • Implementação de Algoritmo Genético Co-Evolutivo com duas populações (RandomForest e KNN)
  • Otimização de hiperparâmetros alcançando F1-score de 98.79% e acurácia de 98.79%
  • Agente LLM com fallback multi-provedor (Gemini, OpenAI, OpenRouter)
  • Avaliação qualitativa do agente alcançando média 4.80/5.0
  • Arquitetura escalável com API REST e interface Streamlit

2. Implementação do Algoritmo Genético e Resultados da Otimização

2.1 Arquitetura Co-Evolutiva

O sistema implementa um algoritmo genético co-evolutivo inovador que mantém duas populações independentes competindo pelo fitness global. Esta abordagem permite explorar eficientemente o espaço de busca de hiperparâmetros para dois tipos de modelos com características distintas.

RandomForest
População 1 - Árvores de Decisão
KNeighbors
População 2 - Baseado em Distância

2.2 Hierarquia de Classes

A implementação segue uma hierarquia orientada a objetos bem definida:

Individuo (ABC) ├── IndividuoRF → Pipeline([('clf', RandomForestClassifier(...))]) └── IndividuoKNN → Pipeline([('scaler', StandardScaler()), ('clf', KNN(...))])

2.4 Função de Fitness

A função de fitness combina duas métricas para lidar com o desbalanceamento de classes:

fitness = F1_weighted × 0.6 + Accuracy × 0.4

Esta abordagem prioriza o F1-score (sensível ao desbalanceamento) enquanto mantém a acurácia como métrica secundária, garantindo que modelos não ignorem classes minoritárias.

2.5 Operadores Genéticos

Crossover Uniforme Adaptado

Implementação customizada de crossover uniforme para dicionários nomeados, onde cada gene tem probabilidade indpb de ser trocado entre os pais:

for key in dict1: if random.random() < indpb: dict1[key], dict2[key] = dict2[key], dict1[key]

Mutação por Agressividade

Sistema de mutação com três níveis de intensidade:

3. Integração com LLMs: Abordagem Sensível ao Gênero

3.1 Arquitetura do Agente ReAct

O agente de saúde nutricional implementa o padrão ReAct (Reasoning and Acting), alternando ciclos de raciocínio e ações para resolver perguntas complexas sobre os dados nutricionais.

Ciclo ReAct: Thought → Action → Action Input → Observation → Final Answer

3.2 Fallback Multi-Provedor Stateful

Implementação inovadora de fallback com memória de sessão para alta disponibilidade:

Características do Fallback:
  • Stateful: O provider descartado não é retentado na mesma sessão
  • Retry Transparente: Perguntas com falha são automaticamente retentadas
  • HTTP 503: Retorna erro de serviço indisponível quando todos falham
  • Configurável: Ordem definida via LLM_PROVIDER_ORDER
Provedor Classe Variáveis de Ambiente
Google Gemini ChatGoogleGenerativeAI GEMINI_API_KEY, GEMINI_MODEL
OpenAI PatchedChatOpenAI OPENAI_API_KEY, OPENAI_MODEL, OPENAI_DROP_STOP
OpenRouter PatchedChatOpenAI OPENROUTER_API_KEY, OPENROUTER_MODEL, OPENROUTER_DROP_STOP

3.3 PatchedChatOpenAI - Auto-Recovery do Parâmetro 'stop'

Modelos de raciocínio da OpenAI (o1, o3-mini, gpt-5-nano) não aceitam o parâmetro stop. A classe PatchedChatOpenAI resolve isso em duas camadas:

Problema: LangChain ReAct injeta stop=["Observation:"] por padrão, causando BadRequestError em modelos de raciocínio.
Solução:
  1. _get_request_payload: Remove stop quando drop_stop=True
  2. _generate: Intercepta BadRequestError e ativa auto-recovery

Decodificação de Categorias

5. Análise de Equidade: Desempenho Entre Grupos Demográficos

5.1 Abordagem para Equidade

O sistema incorpora múltiplas camadas para promover equidade na análise nutricional:

Engenharia de Features Sensível

  • Decodificação de SG_SEXO para rótulos legíveis (Masculino/Feminino)
  • Preservação de DS_FASE_VIDA para análise por faixa etária
  • Inclusão de NU_IDADE_ANO como contínuo para granularidade

Fitness Function com F1-Weighted

A função de fitness prioriza F1-weighted (60%) sobre acurácia (40%), penalizando modelos que ignoram classes minoritárias como "Baixo peso" e "Obesidade Grave".

Capacidade de Análise pelo Agente LLM

O agente pode realizar análises estratificadas por grupos demográficos através da ferramenta filter_nutrition_records:

Exemplos de queries estratificadas: - SG_SEXO == 'Masculino' - SG_SEXO == 'Feminino' & NU_IDADE_ANO > 60 - DS_FASE_VIDA == 'Adolescente' & Prediction == 'Obesidade'

5.2 Considerações de Viés

Potenciais Fontes de Viés:
  • Viés de Dados: O dataset SISVAN pode refletir desigualdades socioeconômicas na acessibilidade aos serviços de saúde
  • Viés de Medição: Peso e altura podem ser reportados de forma diferente por grupos demográficos
  • Viés de Modelo: RandomForest pode perpetuar padrões históricos nos dados de treinamento

5.3 Mitigações Implementadas

Estratégias de Mitigação:
  • Validação Cruzada Estratificada: k-Fold CV mantém proporção de classes em cada fold
  • F1-Weighted no Fitness: Incentiva desempenho equilibrado entre classes
  • Transparência do Agente: O agente LLM recusa inventar dados não disponíveis
  • Interface de Análise: Ferramentas permitem análise explícita por grupos demográficos

5.4 Recomendações Futuras

  • Implementar métricas de equidade (demographic parity, equalized odds)
  • Análise de disparate impact por grupos demográficos
  • Ajuste de thresholds por grupo se necessário
  • Auditoria regular de viés em produção

6. Desafios Enfrentados e Soluções Implementadas

6.1 Desafios Técnicos

Desafio 1: Extração de Arquivos .RAR

Problema: O dataset SISVAN é distribuído em formato .RAR, exigindo extração automática.

Solução: Implementação usando patoolib com unrar-free no Docker para compatibilidade com Debian trixie.

Desafio 2: Monitoramento em Tempo Real do GA

Problema: O algoritmo genético pode levar minutos para concluir, exigindo monitoramento progressivo.

Solução: Sistema de snapshots incrementais em JSONL com polling via API REST para atualização fluida do dashboard.

Desafio 3: Rate Limit em APIs LLM

Problema: Provedores LLM impõem limites de taxa que interrompem o serviço.

Solução: Fallback stateful multi-provedor com avanço permanente e retry transparente.

Desafio 4: Parâmetro 'stop' em Modelos de Raciocínio

Problema: Modelos o1/o3 da OpenAI não aceitam o parâmetro 'stop' injetado pelo LangChain.

Solução: Classe PatchedChatOpenAI com auto-recovery em duas camadas.

6.2 Desafios de Arquitetura

Desafio 5: Jobs Assíncronos de Longa Duração

Problema: Operações de pré-processamento e tuning podem bloquear a interface.

Solução: FastAPI BackgroundTasks com job store em memória e polling reativo.

Desafio 6: Co-evolução de Populações Heterogêneas

Problema: RF e KNN possuem hiperparâmetros não intercambiáveis.

Solução: Seleção global com elitismo estrutural mínimo para evitar extinção de tipos.

6.3 Desafios de Qualidade

Desafio 7: Avaliação de Qualidade do LLM

Problema: Métricas automáticas (BLEU/ROUGE) não medem correção clínica.

Solução: Protocolo de avaliação qualitativa com rubrica humana e verificação factual determinística.

Desafio 8: Alucinação em Dados Inexistentes

Problema: LLMs podem tentar "estimar" valores para perguntas fora do escopo.

Solução: Guardrails no prompt e verificação de disponibilidade de colunas.

7. Considerações Éticas: Privacidade, Bias e Impacto Social

7.1 Privacidade e Proteção de Dados

Medidas de Privacidade Implementadas:
  • Armazenamento Local: Dados processados são mantidos localmente no container Docker
  • Sem PII Externa: Nenhuma informação pessoal identificável é enviada a APIs externas além do necessário
  • Controle de Acesso: API REST com CORS configurado para origens específicas
  • Logs Sanitizados: Sistema de logging evita registrar informações sensíveis

7.2 Viés e Equidade

Riscos de Viés Identificados:
  • Viés de Representação: Populações marginalizadas podem estar sub-representadas no dataset
  • Viés de Medição: Dados antropométricos podem ser menos precisos em certos grupos
  • Viés Algorítmico: O modelo pode perpetuar disparidades de saúde existentes
Mitigações de Viés:
  • F1-weighted no fitness para penalizar desbalanceamento de classes
  • Validação cruzada estratificada
  • Transparência nas recomendações do agente LLM
  • Capacidade de análise estratificada por grupos demográficos

7.3 Impacto Social

Impactos Positivos Potenciais:

  • Detecção Precoce: Identificação automática de riscos nutricionais em larga escala
  • Alocação de Recursos: Direcionamento eficiente de recursos de saúde para grupos de risco
  • Educação em Saúde: Agente LLM fornece informações clínicas acessíveis
  • Monitoramento Populacional: Ferramenta para vigilância nutricional em saúde pública

Riscos Potenciais:

  • Estigmatização: Classificação incorreta pode causar distress psicológico
  • Automatização Excessiva: Sobre-reliância em IA pode substituir julgamento clínico
  • Viés Sistêmico: Modelos podem reforçar desigualdades existentes

7.4 Recomendações Éticas

Para Implementação em Produção:
  • Revisão por comitê de ética antes de deployment clínico
  • Auditoria regular de viés e disparidade
  • Mecanismo de feedback e correção por profissionais de saúde
  • Transparência sobre limitações do sistema aos usuários
  • Consentimento informado para uso de dados
  • Manutenção de supervisão humana em decisões críticas

7.5 Conformidade Regulatory

  • LGPD: Sistema projetado com princípios de minimização de dados e propósito específico
  • Resolução CNS: Alinhado com princípios de vigilância alimentar e nutricional
  • Transparência: Documentação técnica completa e código aberto
